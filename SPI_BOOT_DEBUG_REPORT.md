# SPI Flash Boot: Debug Report

This document records the investigation into a boot hang on the SPI flash read path, the root cause found, the fix applied, and what has (and hasn't) been verified since. Written 2026-09-10.

## Symptom

The Ibex CPU's `hardware_spi_bootloader()` (`firmware/bootloader.c`) writes `0x00000101` to the SPI controller's `REG_STATUS` register (`0x2002_0000`) to trigger a flash read, then polls `tx_done`/status bits in a `while` loop. The CPU got stuck in that loop forever — the SPI transfer never appeared to start.

## Investigation

1. Traced the AHB → APB bridge (`AHB2APB/AHB_APB_Bridge.sv`) and confirmed it correctly executes the APB write protocol (`PSEL`/`PENABLE`/`PWRITE`/`PWDATA` all asserted correctly for one `HCLK` cycle during the access phase). A separate bridge state-machine bug (mishandling back-to-back transactions) was found and fixed here first.
2. Initial hypothesis was a race inside `apb_spi_master-master/spi_master_apb_if.sv`: `spi_rd` is only held high for one clock cycle after the `REG_STATUS` write, and it was suspected the SPI FSM in `spi_master_controller.sv` was missing that one-cycle pulse. **This hypothesis did not hold up** — `spi_rd` feeds a combinational `always_comb` block that re-evaluates every delta cycle, so a single-cycle pulse is sufficient for a same-clock-domain design; there was no race there.
3. Added `$display` traces inside `spi_master_apb_if.sv` (fires only when `PSEL && PENABLE && PWRITE` is true) and `spi_master_controller.sv` (state/state_next/spi_rd/spi_cs every cycle), then ran the Vivado XSim testbench and inspected the console log.
4. **The trace revealed the real bug**: most APB writes targeting the SPI peripheral (`0x2002_0xxx`) never produced a matching `[SPI_APB] APB Write to Addr ...` print — meaning the SPI module's `PSEL && PENABLE && PWRITE` condition was false when the bridge was clearly driving those signals asserted. Writes were being silently dropped, including the critical `REG_STATUS` trigger write.
5. Traced why: `apb_spi_master` (`apb_spi_master-master/apb_spi_master.sv`) has a single clock input, `HCLK`, used internally for both the APB register file and the SPI shift-register FSM. At the top-level instantiation (`NM32_top_temp/NM32_top_temp.srcs/sources_1/new/NM32_top.sv:1105`), this was wired to `pclk` — a clock generated by a simple divide-by-2 toggle flip-flop off `clk` (`pclk_reg <= ~pclk_reg`). Every other APB peripheral (I2S RX/TX, GPIO, DMA) is wired with **both** `.HCLK(clk)` and `.PCLK(pclk)`, keeping their core logic on the same clock domain as the bridge. The SPI module alone was on the wrong (divided, half-rate) clock.
6. Since the AHB→APB bridge (on `clk`) only holds `PENABLE` high for exactly one `clk` cycle, and the SPI module only sampled the bus on `pclk` edges (occurring every 2 `clk` cycles), any transaction whose `PENABLE` pulse didn't happen to align with a `pclk` edge was missed entirely — explaining the intermittent, "1-in-6 or so" write pattern seen in the trace.

## Root Cause

`apb_spi_master`'s `HCLK` port was wired to the divided `pclk` instead of the full-rate `clk`, creating an unintended clock-domain mismatch against the AHB→APB bridge, which drives single-`clk`-cycle APB transactions. The SPI module intermittently missed writes, including the `REG_STATUS` trigger, so `spi_rd` was often never actually asserted — causing the boot-time polling loop to spin forever.

## Fix

One-line change in `NM32_top_temp/NM32_top_temp.srcs/sources_1/new/NM32_top.sv`:

```diff
     ) spi_inst (
-    .HCLK   (pclk),
+    .HCLK   (clk),
     .HRESETn(rstn),
```

**Caveat carried forward, not yet independently verified:** `apb_spi_master`'s internal SPI serial-clock generator divides `HCLK` by the firmware-configured `spi_clk_div` (`REG_CLKDIV`, written as `4` in `firmware/bootloader.c`). Since `HCLK` now runs at full `clk` speed (150–200 MHz per `NM32_SoC_Spec_2.0.md`) instead of half (`pclk`, 75–100 MHz), the resulting SPI bus clock is now roughly 2x faster than it was before this fix, for the same divider value. This hasn't caused any problems in simulation (the behavioral flash model has no real timing constraints), but should be checked against the target flash part's actual timing spec before this goes to real hardware.

## Verification Done So Far

All verification was done via Vivado XSim (`vivado -mode batch -source ...`), reading `$display` trace output — no waveform analysis was needed once the traces were in place.

- **Confirmed**: after the fix, every `[SPI_APB] APB Write to Addr N` line has a matching bridge-driven write — no more dropped transactions.
- **Confirmed**: the first `REG_STATUS` trigger write (`0x00000101`) correctly set `spi_rd=1`, and the SPI FSM left `IDLE` into the `CMD` state.
- **Confirmed**: the first full SPI transaction (8-bit CMD + 24-bit ADDR + 32-bit DATA) completed cleanly — `[FLASH] Captured Command = 0x03`, FSM returned to `IDLE`, `spi_cs` deasserted.
- **Confirmed**: the CPU's polling loop actually exits after that transaction and proceeds into new code (`ret`, then genuinely new instruction addresses) — the original hang is resolved.
- **Confirmed over a longer batch run (5ms simulated, ~86s wall-clock)**: 713 consecutive SPI word-read transactions executed cleanly with no dropped writes and no `ERROR`/`CRITICAL WARNING` in the log, at a steady ~7.02µs/word. The flash byte address read back (`[FLASH] Captured Address`) increments monotonically by 4 every transaction, exactly as expected for a sequential word-by-word copy.
- **Explained, not a bug**: this long sequential read is `hardware_spi_bootloader()` in `firmware/bootloader.c` streaming the compiled firmware's `.text` section from external SPI flash into internal RAM, one 32-bit word at a time via `read_spi_flash_word()`. Checked against the actual build: `.text` is `0x1d2c` = 7468 bytes = 1867 words (`readelf -S firmware.elf`, matches `firmware_flash.bin`'s size on disk exactly). At 5ms in, the loop had completed 711/1867 words (~38%), consistent with the observed per-word rate — full copy is expected to take roughly 13.1ms of simulated time. `.data` is empty (all globals are zero-initialized `.bss`, not streamed from flash).

## Update: DMA Hang (found, fixed, then superseded)

After the SPI fix, a longer batch run (25ms) confirmed the `.text` copy loop finishes at **`Time≈13.10ms`** (matches the `.text` size math: `0x1d2c` = 7468 bytes = 1867 words), then `main()` runs and — at the time — called `pack_and_start_dma()`/`wait_and_unpack_dma()` for I2S streaming. This hung the same way the SPI boot had:

- `pack_and_start_dma` correctly configured both DMA engines' `SRC`/`DST`/`LEN`/`CTRL` registers (verified against `main.c`'s expected values).
- `wait_and_unpack_dma` then polled `DMA_RX_STATUS` (`0x2003_0010`) forever — 61,694+ poll iterations with no completion, confirmed against the exact opcode encoding at `0x30000044-0x30000050` (`lw`/`andi`/`beqz`).

Root-caused via targeted `$display` instrumentation added to `ahb_decoder_and_arbiter/ahb_arbiter.v` (removed again once done) to two **separate** bugs in `NM32_top.sv`, both fixed and confirmed via the arbiter trace (`master_sel` was seen reaching `2`/`3`, the DMA master indices, only after both fixes):

1. A leftover tie-off `generate for(i=2; i<15; ...)` loop (present in the version of `NM32_top.sv` at the time, which had two separate DMA masters at indices 2 and 3) was force-driving `mst_hbusreq[i]` (and `mst_haddr`/`mst_htrans`/etc.) to `0` for those same indices — directly conflicting with the DMA modules' own output ports on the same wires. Fixed by starting the loop at index 4 instead of 2.
2. `dma_controller`'s APB register-write block is clocked on `PCLK`, same as the original SPI bug — `.PCLK(pclk)` in the instantiation created the same single-`clk`-cycle-pulse-vs-divided-clock mismatch. Fixed by wiring `.PCLK(clk)`.

**Note:** `NM32_top.sv` has since been substantially reworked by the user (CPU swapped from Ibex to PicoRV32, DMA consolidated to a single instance at master index 1, `main.c` no longer uses DMA at all — see below). The tie-off-loop conflict (bug 1) doesn't recur in the reworked file since only master index 1 is used and the loop already starts at 2. The `PCLK`/`clk` mismatch (bug 2) does still exist in the reworked file's single `dma_inst` and was fixed there too, but is currently moot since `main.c` doesn't call the DMA path anymore.

## Update: CPU Swapped to PicoRV32 — New Reset-Vector Bug (found and fixed)

The user reworked `NM32_top.sv` mid-session: the CPU changed from Ibex to **PicoRV32** (`picorv32` instantiated directly, single AHB master via a `pico_to_ahb` wrapper, `NUM_ARB_MSTS` dropped from 4 to 2), and the DMA was consolidated into one `dma_inst` at master index 1.

This introduced a new, unrelated hang: PicoRV32 was instantiated with `.PROGADDR_RESET(32'h0000_0000)`, so it starts fetching at address `0`. But `firmware/sections.ld` places the `.boot` section at `0x80` — a convention specific to **Ibex**, which auto-jumps to `boot_addr_i + 0x80` on reset. With PicoRV32 resetting straight to `0x0` instead, the CPU fetched invalid/empty ROM content and immediately trapped into an infinite loop at address `0x38` (the illegal-instruction/IRQ handler spin-loop), before ever reaching real code.

**Fix:** changed `.PROGADDR_RESET(32'h0000_0080)` to match where `sections.ld` actually places the boot code. Verified via a 1ms batch run: the `Addr=0x00000038` spin loop no longer appears, and the CPU proceeds into the SPI boot copy loop as expected (217 flash-word transactions completed within 1ms, no errors).

## Update: I2S Hang (found, fixed) — Same Bug Pattern a Fourth Time

`main.c` was rewritten to drop DMA entirely in favor of direct polling I/O (`while (I2S_TX_LEVEL > 14) ; I2S_TX_DATA = ...;` / `while (I2S_RX_LEVEL == 0) ;`, in `io_hop()`). This hung immediately: `I2S_RX_LEVEL` never went nonzero, and — tellingly — `I2S TX FIFO WRITE` count was `0` even though `init_i2s()` unconditionally writes `I2S_TX_DATA` eight times during boot.

This turned out to be **the exact same clock-domain bug, a fourth time**: `EF_I2S_APB`/`EF_I2S_TX_APB` (`I2S/EF_I2S_APB.v`, `I2S/EF_I2S_TX_APB.v`) clock every register-write block on `PCLK` alone, and both were wired to the divided `pclk` at the top level, same as the SPI and DMA bugs. Fixed by changing `.PCLK(pclk)` → `.PCLK(clk)` for both `i2s_apb` and `i2s_tx_apb` instantiations in `NM32_top.sv`.

**Note:** `EF_GPIO8_APB` (`gpio_apb_inst`) still has `.PCLK(pclk)` and was not changed, since GPIO isn't touched anywhere in the current firmware path and fixing it wasn't necessary to unblock verification. If GPIO is used later, check it for the same bug first.

**Verified via a 40ms batch run:** `[SERIALIZER]` (the testbench's simulated I2S RX stimulus, driven by the I2S TX clock looped back to RX per `tb.sv`) went from firing **once** (just the reset-time initial load) to firing **773 times** — confirming the I2S clock is now actually toggling and real audio samples are flowing in. Execution progressed steadily through new code with no repeated/stuck program-counter pattern.

## Final Verification: Full Pipeline Confirmed Working End-to-End

A 60ms batch run (all five fixes applied: SPI clock, DMA clock, PicoRV32 reset vector, I2S RX clock, I2S TX clock) shows the complete audio pipeline actually executing, in order:

| Time | Event |
|---|---|
| ~13.1ms | `.text` SPI flash copy loop completes |
| 35.94ms | `PING_PONG_CTRL = 0` — frame loop starts (frame 0) |
| 38.88ms | `FFT_CTRL = 1` — frame 0 FFT triggered |
| 49.19ms | `IFFT_CTRL = 1` — frame 0 IFFT triggered (implies FFT completed and the mask stage ran in between) |
| 51.31ms | `PING_PONG_CTRL = 1` — frame 0 fully finished (including `io_hop` drain), loop advances to frame 1 |
| 54.25ms | `FFT_CTRL = 1` again — frame 1 FFT triggered, confirming the loop genuinely repeats |

Zero `ERROR`/`CRITICAL WARNING` anywhere in the 60ms log. This is the first time in this investigation the design has been observed completing a real frame and looping to the next one.

## Summary of All Fixes Applied

All five are the same underlying bug class except the last: a peripheral's internal register-write logic was clocked on `PCLK` (the divided, half-rate `pclk`) while the AHB→APB bridge only ever holds `PENABLE` high for one full-rate `clk` cycle — so writes landed intermittently or never, depending on clock-edge alignment.

1. `apb_spi_master` (`spi_inst`): `.HCLK(pclk)` → `.HCLK(clk)`
2. `dma_controller` (`dma_rx_inst`/`dma_tx_inst`, later consolidated to `dma_inst`): `.PCLK(pclk)` → `.PCLK(clk)`
3. `EF_I2S_APB` (`i2s_apb`): `.PCLK(pclk)` → `.PCLK(clk)`
4. `EF_I2S_TX_APB` (`i2s_tx_apb`): `.PCLK(pclk)` → `.PCLK(clk)`
5. **Different root cause** — PicoRV32 (`cpu`, after the CPU was swapped from Ibex): `.PROGADDR_RESET(32'h0000_0000)` → `.PROGADDR_RESET(32'h0000_0080)`, matching where `sections.ld` actually places the `.boot` section (an Ibex-specific `reset + 0x80` convention that PicoRV32, which resets straight to address 0, needs to be told about explicitly).

Also fixed along the way, now superseded/moot but still correct: a leftover tie-off `generate` loop in `NM32_top.sv` was force-driving `mst_hbusreq[2]`/`[3]` (and related AHB signals) to `0`, conflicting with two separate DMA master instances that existed at those indices in an earlier version of the file. Fixed by starting the loop at index 4. Not applicable to the current single-DMA-master version of the file, where the loop already starts clear of the one DMA master index in use.

## Not Yet Verified

- No full waveform/value-level check that the FFT/IFFT/mask math produces numerically correct audio — only that the control-flow sequence (trigger → done → next stage) executes without hanging or erroring.
- `EF_GPIO8_APB` likely has the same `PCLK` clock-domain bug, unfixed (see above) — not currently exercised by firmware, so unconfirmed.
- `trigger_vecs_q15` in `main.c` was a placeholder (`{0}`) as of the last read of that file — worth re-checking, since even with the pipeline now running, suppression won't be meaningful without real trigger-vector data.
- Frame timing (~15-16ms simulated time per frame based on the 38.88ms→54.25ms gap between FFT triggers) has not been checked against any real-time audio deadline.
